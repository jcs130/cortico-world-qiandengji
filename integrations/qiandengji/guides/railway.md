## 铁路设计与连通性

这份资料由维护人员提供：包含 Minecraft Java 1.20.6 的轨道状态基线、交通网络的检查方法和可供你选择的设计建议。它不是你已经掌握或亲历成功的证明。当前服务端、已加载方块状态和实际试乘优先；不要把现实铁路公式当作 Minecraft 的运动规则。

### 先设计一条值得坐的线

先确定这条线服务谁、连接哪两个入口：住宅到据点、运货、观景，或几种用途兼顾。起终站要让人走得到、上得车、下得来，线路应避开农田、门口、他人建筑和未来扩建的位置。把路线中心线、轨道高度、站台与进出通道分别画出来；轨道层、支撑层和人的脚格不是同一高度。

有明显取舍时比较少量候选：直达线可能较短，但要拆山或穿过院子；顺地形的弯线可能较长，却能保留景观、降低施工量。用实际长度、升降、弯折、拆改量、材料、入口方便程度与想展示的景色说明选择。最短路只是一个指标，没有固定权重或统一审美分数。

美感可以从这些可观察的问题入手，自选风格：
- 路基是否连续、宽度有意保持一致，露出的泥土高柱是否需要做成有支墩的桥或顺坡收边？不要为了装饰自动拆掉承重格。
- 枕木、石砟/路基、栏杆、站台与灯具是否形成清楚的层次？选择少量主材和点缀，让重复的节奏有规律，避免每格换材料和随意堆箱子。
- 进站前是否留出缓冲段，站台、候车区、按钮和出口是否一眼能理解？灯、顶棚和标牌不要侵入车辆及乘客空间。
- 地形变化能否处理成短桥、挡墙、隧道入口或观景段？桥墩、边坡与地面接合，尽量保留原来的树、水岸和房屋视线。

先看目标工地的实际画面，再做小段原型，从远景看轮廓、近景看站台和接缝、乘客视角看沿途。`mymc_visual` 的 focus 不会把镜头移到工地；不在现场或截图失败时，美感未验证。用户说不好看是修订依据；不要用方块数、工具成功或自己给的分数替代用户观感。较大的改造沿用 building 资料中的蓝图、保护、材料和施工对账。

### 把轨道当成有方向和高度的网络

每根轨道是一段只有两个端口的线。相邻两格有轨道还不够：两边端口必须朝向彼此，并在相同接合高度相接。普通轨道有直线、四种弯道及四种升坡；动力、探测、激活铁轨的原版状态没有弯道。三个方向紧贴一格不会同时变成三岔道；岔口只以当前实际 shape 为准，切换后重读。

方位：north 为 z−，south 为 z+，east 为 x+，west 为 x−。`ascending_east` 是西侧低、东侧高；高端接到邻格 y+1 的轨道或相容坡段。`north_east` 只接北和东，不接南或西。新放相邻轨道可能改变旧轨的形状；施工后读 `block.getProperties().shape`，不要沿用蓝图里的预想朝向。

`mymc_railway {"bounds":[xmin,ymin,zmin,xmax,ymax,zmax],"start":[x,y,z],"end":[x,y,z],"detail":true}` 只读当前连接已加载的方块，不抢身体、不移动、不点红石。bounds 为绝对坐标、含端点，最多 4096 格、每轴 128 格、256 根轨道。覆盖路线、相邻格与上下接合高度即可，长线分段，保留共同的接合轨道和采样时间，不把大盒子全读进上下文。

- `components` 是当前 shape/高度真正互接的连通分量；`route.path` 是本次样本内的端口路径，轨道数量达标不能替代它。
- 判断这次指定的起终点，读 `route.status/path`；其他分量可能是另一股道或施工余段，不会撤销已经测得的这条连接。不要只因 `componentCount>1` 就拆改一条已连通的路径；它也不证明整个目标线路已完工。
- `connected_in_sample` 仅证明样本内存在静态连接；`not_connected_in_sample` 表示没测到这样的路径；`unknown` 表示缺少端口/已加载区域等证据，不能宣称全局不可达。
- 默认摘要保留完整计数与指定路径，但只列有限示例；看 `componentsOmitted`、`openPortsOmitted` 和 `unpoweredExamplesOmitted`，示例不等于完整列表。回执最多 7500 字符，`detail:true` 超限会要求缩小范围，不返回截断明细。
- `openPorts` 给出示例接头的朝向、接合高度、相邻实际方块或朝向不匹配；终点开口可能是有意设计。需要时缩小到那个接头。
- detail 的 `rails` 每行为 `[x,y,z,palette,component]`，palette 索引 `railPalette`；`edges` 的数字是 rails 数组的零起下标。它们可交给你自己的程序分析、做示意图和比较修订。
- `collisionExamples` 是支撑/头顶的碰撞读数，不是完整乘客扫掠体检查。弯道侧面、斜坡高端、隧道顶部、站台边缘还要查 vision 的体素/射线并实乘。未加载和盒外保持未知。

### 能通车、能发车、好乘坐分别验证

动力铁轨、探测铁轨、激活铁轨用途不同：动力轨提供驱动，探测轨检测过车发红石信号，激活轨作用于车辆。激活轨不是加速轨，有电时还可能导致乘客下车。动力轨未供电通常会制动，但站台制动段本来就可以这样设计；`powered:false` 只是一瞬间的状态，不等于电路坏了。

原版静止车辆的发车需要方向条件，例如端点背后的实心挡块、合适的坡度或初始推力；只亮一根平地动力轨不能证明车会按预期启动。按钮接到哪一格、信号持续多久、哪几根轨 powered 变化、车的起终点和速度，要在当前版本用小段实际验证。邻格亮灯不等于动力轨通电。上坡需要克服高度与速度损失，未供电段可能让车停住；不要背诵固定“每隔多少格一根动力轨”而省略载人往返测试。

先静态查接头，再在安全小段试发车；要判断发车，比较同一车辆的起终坐标与时间。再测完整去程、停车/下车和回程，记录站台可达与头顶/侧面碰撞。空车通过不证明载人通过，单向下坡通过不证明反向上坡通过。发现卡住时先核对是否还在矿车上；普通 goto 走不动不能直接推断地形有深沟，ride off 的具体契约用帮助查询。

### 让经验变成你自己可修订的方法

现有 Mineflayer 的 `bot.blockAt`、`getProperties`、挖掘和放置接口继续使用，查 control 资料与 `mymc_script {"api":"index"}`。铁路读数补的是整段网络关系，不代替这些原生动作，也不替你选择路线或自动施工。

拆改指定格与采集同类材料不是一回事。`collect` 没有 `at` 字段，带指定坐标时整单拒绝；按帮助使用已有 `excavate` 的 shape/anchors（单格 box 的两个锚点相同），或用已暴露的原生 `blockAt→dig` 接口。之后回读被改格及相邻轨形，避免从别处拿走一根轨、目标格仍未变化。

有重复、可评价的步骤时，你可以自己写有界 JavaScript：读取当前接头→检查端口/支撑与权限→选择少量可逆改动→执行→重新读相邻轨形状和路径→保留或回退。用 `validate:true` 做语法检查，再用运行号及完整 SDK 回执核对真实效果；稳定后通过现役 procedure 工具保存版本、依赖、适用条件和失败边界，按需检索。不要每轮全文重读或为了学习改动已在正常工作的线路。

评价分开记：静态连接是否改善、实际往返是否成功、碰撞/停滞和材料是否减少、画面与用户反馈是否更满意。标明作者、父版本、源码哈希、任务/运行号、时间和区块覆盖；维护人员提供的读数工具或范例不算你自主学会。没有试乘、美感反馈或可比场景时就留待验证，失败反例也保留。

### 资料入口与适用范围

- Mojang：[Taking Inventory: Rails](https://www.minecraft.net/en-us/article/taking-inventory--rails)、[Taking Inventory: Minecart](https://www.minecraft.net/en-us/article/taking-inventory--minecart)：铁轨种类和基础乘车/驱动。
- [Mineflayer 公共 API](https://github.com/PrismarineJS/mineflayer/blob/master/docs/api.md) 与 [prismarine-block](https://github.com/PrismarineJS/prismarine-block)：现场方块、属性及碰撞；本部署固定 Mineflayer 4.37.1 / Java 1.20.6，后续主分支文档不等于现役接口。
- [NetworkX 连通分量](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.components.connected_components.html)：把网络分成真正互通的部分，以及广度优先搜路的思路；这里用端口和高度构边，不是把所有相邻格直接连起来。
- 现实交通设计可借鉴主线/支线、枢纽/站台、分流、缓冲段和路线成本的概念；现实的曲率、超高、摩擦公式不直接预测 Minecraft 方块弯道。服务器插件改变速度、技能或传送时，另查当前说明与回执。
